## 1. 任务数据

### P1.1 评测集：Final-200 是历史整理产物，不是冻结基准

- **V1 现状**：`scripts/build_comparison_report.py` 等一整套评测围绕 Final-200 组织；它是仓库后续整理的历史评测集，与论文/源数据的 1,459 条 eval split 不对应，且没有冻结与访问控制约定。
- **V2 修改（F1.1）**：最终评测集改为源数据全部 1,459 条 `tag=eval`（自然分布：easy 206 / medium 788 / hard 465）。作为冻结 holdout：不用于训练、调参、checkpoint 选择、Rubric 迭代。Final-200 退役，不参与 V2 正式指标。
- **来源**：基线 §3、§4.4。

### P1.2 Query 与 Gold 的一致性从未被验收

- **V1 现状**：源数据 23,421 条按"提示词 ↔ 目标商品"一对一构造，隐含假设每条 Gold 满足 Query，但从未系统性核验；也没有换 Gold、淘汰坏任务的流程。
- **V2 修改（F1.2）**：两级全量验收。第一级代码硬约束（ASIN 存在、字段完整、预算/必选规格/品牌类别可编程检查对 Gold 核验）；第二级 Jev 语义验收（satisfies / partial / no / unverifiable，与 Reward 同 Judge）。训练任务验收失败先换 Gold（同 category/domain 检索 + 硬约束 + Jev 确认），换不到则出局。评测任务保留原记录并标记 invalid / unverifiable，最终报告总量 / 可评分量 / 两类比率。
- **来源**：基线 §4.2。

### P1.3 画像由商品—指令对反向生成，目标条件偏差直接泄漏

- **V1 现状**：画像从既有商品—指令对反向构造。实测确认泄漏：`user_persona.行为特征.最近14天搜索关键词` 原文包含目标商品描述（如目标为乳胶枕时搜索词即"带满天星图案适合5岁小孩的泰国进口乳胶枕"）。画像与目标商品强绑定，等于把答案写进用户档案。
- **V2 修改（F1.3）**：不复现论文个性化 benchmark。三条件画像 `no_profile / aligned / irrelevant`（50/25/25），每条 Query 只属一种条件。`aligned` 用自带画像清洗后优先 + 画像池语义匹配补齐（训练集缺口约 2,200 条）；`irrelevant` 跨领域重配 + 语义复核。泄漏字段不删库，通过泄漏标签管理可用性。画像只是软偏好，明确请求优先。
- **来源**：基线 §4.3；泄漏字段实测 2026-09-23。

### P1.4 无系统性难度定义

- **V1 现状**：难度未进入任务组织；`scripts/label_sft_difficulty.py` 存在但无统一冻结规则。
- **V2 修改（F1.4）**：二维规则 `easy: attributes<4 且 combinations<=7；hard: attributes>=9 或 combinations>=21；medium: 其余`，全量已复算（train 18.0/58.8/23.2%，eval 14.1/54.0/31.9%）。domain/category 只做二级覆盖。第一版不合成无解任务。
- **来源**：基线 §4.1。

### P1.5 无独立开发集

- **V1 现状**：训练过程没有与训练数据隔离、分层抽样的 dev set；checkpoint 与规则迭代缺少固定参照。
- **V2 修改（F1.5）**：从验收后训练池分层抽约 1,050 条（5%），分层骨架 difficulty × domain × 画像条件（81 格，实测最小格约 20 条）。不进 SFT / GRPO。
- **来源**：基线 §4.4。

### P1.6 定向补充数据无规矩

- **V1 现状**：无对应流程。
- **V2 修改（F1.6）**：第一版不补、不预设流程；验收损失如实报告，损失大到影响训练量或分布时再单独讨论。
- **来源**：用户 2026-09-23 决定。

## 2. Reward 与评测

### P2.1 `valid_alternative=0.55` 的 Gold 特权

- **V1 现状**：`reward.py` DEFAULT_REWARDS 中 `gold_purchase=1.0`、`valid_alternative_purchase=0.55`。商品库中存在多个等价满足需求的商品时，模型被教导"非 Gold 不买"，替代品收益打折。
- **V2 修改（F2.1）**：完全满足用户需求的替代品与 Gold 同为 1.0，取消目标商品特权。
- **来源**：基线 §7。

### P2.2 灰区判断靠代码文本匹配，语义等价无法识别

- **V1 现状**：`valid_alternative / partial` 的判定来自 `_preference_dimensions` 的加权文本比较（brand 别名匹配、model / core_functions / key_options 字符串比对）。"护颈椎"与"保护颈部脊柱"、"天然乳胶"与不同表述方式对不上；partial 分数是文本匹配率的线性映射（[-0.30, 0.25]），匹配率本身不可靠。
- **V2 修改（F2.2）**：三段分流保留（Gold ASIN 代码判满分 / 硬约束代码判错 / 灰区语义判断），灰区判断器换成 Jev（`typesafe/jev-1.13` 固定版本），单一 Choice 四分类 `fully_satisfies / partially_satisfies / does_not_satisfy / insufficient_evidence`。输入仅含实际请求、可选画像、真实候选字段、所选 options、成交价格；不含 Gold、轨迹、DOM。partial 固定 0.25，不再用文本匹配率连续打分。
- **来源**：基线 §7。

### P2.3 判分器从未校准

- **V1 现状**：Reward 判断（无论文本匹配还是任何语义组件）没有对照人工标注的校准集，判分可信度未知。
- **V2 修改（F2.3）**：300 条校准集（Gold 验收场景 150 + 灰区场景 150），GLM 预标 + 用户裁决约 100 条分歧与低置信样本；冻结标准：Jev `fully_satisfies` 精确率 >=95%、整体一致率 >=85%；通过后冻结版本/提示词/阈值，不再改动。
- **来源**：基线 §7，2026-09-23 确认。

### P2.4 评测报告的分析结论人工硬编码

- **V1 现状**：`build_comparison_report.py` 的 MODEL_ANALYSIS 字典把每个模型的 bad case 结论（画像、要点、修复建议）写死在脚本里，是针对一次 Final-200 运行的人工总结，不可复用于新运行；评测口径也偏单一汇总。
- **V2 修改（F2.4）**：主指标 = 可评分任务上的完成率（Gold 或 Jev fully_satisfies）；小分按 difficulty / 画像条件 / domain 三维切分；次要指标副表（步数、放弃率、超时率、基础设施失败率）；错误归因固定四类（买错 / 违反硬约束 / 未购买 / 系统故障），bad case 按类别回流。报告数据全部由固定管线从轨迹自动生成。
- **来源**：基线 §7，2026-09-23 确认。

### P2.5 Reward 数值表整体

- **V2 修改（F2.5）**：**保留 V1 Reward v3 数值为基础**，仅改两处（F2.1、F2.2 的 0.25）。wrong_purchase -0.85（最重）、graceful_stop -0.15、early_abstain -0.35、max_steps -0.50、repeat_loop -0.65 全部沿用；不可验证样本从 GRPO 组内剔除。设计立场：买错罚最重，宁可明确退出不乱买。
- **来源**：2026-09-23 讨论（用户质疑后确认沿用 v3，避免不必要的改动）。

## 3. Teacher 与 SFT

### P3.1 轨迹验收与判分标准脱节，存在简单拒绝采样风险

- **V1 现状**：SFT 采集（`collect_sft_data.py` / `collection/sft.py`）的验收口径与评测判分不是同一套；基线明确"不能只保留成功样本做简单拒绝采样"，原始轨迹缺少系统化的失败分类保留。
- **V2 修改（F3.1）**：Teacher 轨迹在 Rubric 冻结后采集；准入 = 与正式评测 Reward 完全同一套判分代码（硬约束 + Jev fully_satisfies + 轨迹良构）。首轮 6,000 任务 × 4 次采样，hard 提升至 >=30%；每题只取 1 条最优进 SFT；全失败任务重试一轮后归入 teacher-hard 队列（留 RL 与错误分析）；原始轨迹全部保留并按五类归因（验收通过 / 近似成功 / 策略失败 / 主动退出 / 基础设施无效）。eval 1,459 永不采集。
- **来源**：基线 §5，2026-09-23 确认。

### P3.2 思考模式导致轨迹过长

- **V1 现状**：rollout 客户端支持 thinking 开关（DeepSeek 类模型需要），思考内容计入轨迹，推高长度与训练成本。
- **V2 修改（F3.2）**：全链路（Teacher / SFT / RL / 评测）关闭思考模式。
- **来源**：用户 2026-09-23 决定。

### P3.3 超长轨迹无处理策略

- **V1 现状**：无显式策略，实际靠 max_steps 与上下文限制硬截轨迹，截断样本进入训练的风险不可见。
- **V2 修改（F3.3）**：超出训练序列长度上限的轨迹直接丢弃（截断保留前半段 = 教模型"搜索后不下单"）；监控丢弃率，>5% 视为轨迹长度与训练上限配错，调整上限而非硬扔。
- **来源**：基线 §5.5，2026-09-23 确认。

### P3.4 loss 边界不可验证

- **V1 现状**：token 拼接与 mask 正确性缺少强制验证环节。
- **V2 修改（F3.4）**：loss 只作用于模型生成的行动 token；observation / prompt / 环境拼接全部 mask；要求验证拼接后的 token 序列与模型真实边界一致（agent loop 冒烟项之一）；SFT 入库做格式与 mask 完整性兜底校验。
- **来源**：基线 §5.5、§6。

## 4. Harness（源自 2B 严格成功率 issue 三项，均有代码实锤）

### P4.1 `tool_choice=auto`，纯文本回复直接终止

- **V1 现状**：`rollout.py:159,167` 发送 `tool_choice="auto"`；`rollout.py:350-354` 无工具调用即标 `assistant_final` 收卷。实测后果（Final-200 对比报告数据）：glm-5.2 的 75 个 bad case 中 49 个以 assistant_final 停止，其中 29 个已完成深度核验甚至选好规格仍没买——不是能力问题，是出口设计让"说"替代了"做"。
- **V2 修改（F4.1）**：环境回合 `tool_choice=required`；结束只通过 `buy_now` 或 `finish_without_purchase` 两个工具表达。移除 `think` 工具（其 schema 描述"不要调用"仅靠提示词劝退；required 下会变成被迫调用的无效出口）。混合"文本 + 工具调用"回复不拒绝：文本保留，工具照常执行；单回合单工具、多余丢弃并记录的现行规则不变。vLLM 0.25.1 / veRL 0.8.0 对 required 的支持列入兼容性冒烟。
- **来源**：用户提供 issue + 代码核实 + build_comparison_report 实测数据，2026-09-23 确认。

### P4.2 详情子页工具低价值重复调用

- **V1 现状**：`view_description / view_features / view_reviews / view_attributes` 随时可调、可无限重复，每次消耗一步（上限 30 步）。实测后果：glm-5.2 成功轨迹平均 9.31 步、比 qwen3.7-max 多约 1.9 步，报告原话"常把 Description、Features、Reviews 全看一遍，即使页面没新增信息"。而结构化详情页已含 title / brand / price / key_attributes / options，子页常常无信息增量。另查实：数据文件无评论字段、环境引擎评论列表从未填充，评论页在当前数据下恒为空页。
- **V2 修改（F4.2，2026-09-24 用户修订）**：环境与工具集完全不动（Environment v2.1 固定契约），四个子页工具全部保留；同一商品同一子页（含评论页）重复访问由动作守卫拦截（不消耗环境步骤，回敬提示），一个轨迹只许翻一次；不做过程奖励，维持终止型 Reward；子页访问占比与重复拦截次数进入轨迹记录与错误归因副表。
- **来源**：用户提供 issue + 代码核实，2026-09-23 确认删 reviews，2026-09-24 修订为保留。

### P4.3 Observation 预算偏小，压缩不区分字段价值

- **V1 现状**：`projection.py` 默认 search 1536 / detail 4096 / generic 768，上下文压缩默认关闭；超预算时对整行统一压缩字符（`_project_structured_search_results` 按统一字符限制压所有字段），不区分 price / options / key_attributes 与自由文本的价值差异。约束相关信息可能被压掉（2B 实验中加大预算后 strict accuracy 到约 50%，说明截断确实在伤结果）。
- **V2 修改（F4.3）**：正式预算按实测 P95 定（目标 95% 页面不截断），试跑临时值 search 3072 / detail 6144 / generic 1024。截断按字段价值排序：动作信息（footer / ASIN / 价格 / 按钮）硬校验必保（现有安全契约保留）；正文先砍自由文本与长标题，key_attributes / available_options 最后砍。监控闭环：按截断分桶统计成功率；与 SFT 超长轨迹丢弃率联动，预算与训练序列长度配平调整。
- **来源**：用户提供 issue + 代码核实，2026-09-23 确认。

## 5. 训练组织与实验设计

### P5.1 无任务池隔离策略

- **V1 现状**：SFT 与 RL 使用任务的关系未定义。
- **V2 修改（F5.1）**：GRPO 优先使用 SFT 未接触的任务（约 12,600 道），耗尽后再循环；避免"背过的原题拿满分"污染 RL 信号与组内梯度。
- **来源**：2026-09-23 确认。

### P5.2 无统一对照设计

- **V1 现状**：无固定对照框架，各次评测之间不可比。
- **V2 修改（F5.2）**：三档主线（原模型零样本 / SFT-only / SFT+GRPO），冻结 1,459 上同一套评测；不做多 RL 算法对比；消融不预设。
- **来源**：2026-09-23 确认。

### P5.3 多条执行路径的协议漂移

- **V1 现状**：采集、验证、训练、评测各有入口，存在配置与协议漂移风险。
- **V2 修改（F5.3）**：Teacher 采集、SFT 后验证、在线 GRPO、最终评测共用同一套环境与 Agent harness；统一 rollout 记录字段（任务版本、采样参数、动作、observation、耗时、终止原因、Reward 明细、Rubric 版本）。Agent Lightning 仅作后续适配器对照。
- **来源**：基线 §6。

## 6. V1 中明确保留、不动的部分

V2 不是重写，以下经核对后直接沿用：

- **Reward v3 数值表**：除 F2.1 / F2.2 两处外全部保留（F2.5）。
- **observation v2 结构化渲染**（`observation.py`）：字段选择与防泄漏守卫（拒绝 goal / reward 等隐藏字段进 observation）。
- **投影安全契约**（`projection.py`）：footer / ASIN / 按钮、搜索页全商品保留的硬校验——V2 只改预算数值与字段优先级，不动契约。
- **动作守卫机制**（`action_reject_reason` + blocked 回敬）：V2 在其上扩规则（子页重复拦截），机制本身保留。
- **单回合单工具调用**：`_enforce_serial_tool_call` 及多余调用丢弃记录。
- **ShopSimulator Environment v2.1 与数据**：环境与 23,421 条数据沿用，只做验收与标注治理。
- **veRL 0.8.0 / vLLM 0.25.1 / Qwen3.5-9B（后训练版）/ 双 A800 BF16 全参 FSDP**：依赖栈不变。
