## 4. 数据与难度设计

### 4.1 主难度轴

- 难度主要由 `attribute × options` 共同决定。
- 第一版使用简单、可解释的二维规则，不做加权总分：
  - `easy`：`attributes < 4` 且 `option_combinations <= 7`；
  - `hard`：`attributes >= 9` 或 `option_combinations >= 21`；
  - `medium`：其余任务。
- `attributes` 直接取原始 `instruction.attributes` 的数量；`option_combinations` 取商品各规格轴可选值数量的笛卡尔积。原始 `attributes` 和 `instruction_options` 标注直接作为可信输入，不做全量重新提取或模型复核；后续发现的明确 bad case 再单独回流修正。
- 按上述阈值，源训练集分布为 `easy=3,950 (18.0%) / medium=12,908 (58.8%) / hard=5,104 (23.2%)`；源评测集自然分布为 `easy=206 (14.1%) / medium=788 (54.0%) / hard=465 (31.9%)`。
- `domain` 和 `category` 是二级覆盖轴，用于避免主要类别或领域缺失，不做高维全组合均衡。
- 训练数据采用受控采样，在覆盖三档难度的同时尽量保持源数据分布近似。
- 最终评测集保持源 eval split 的自然商品、属性、选项、领域和类别分布。
- V2.0 第一版不额外合成无解任务，训练与评测任务都保持可解。

### 4.2 Query 与 Gold 治理

- V2.0 以现有 21,962 条训练 Query 为主体，不全量重生成；先重新验收，只对坏数据和分布缺口做定向修复或补充。
- Query 表达用户需求，Gold 只是参考答案。Query 与原始 Gold 冲突时，不为了迁就 Gold 改写用户需求。
- 训练任务的原 Gold 不满足 Query 时，优先从商品库重新指定可靠 Gold；找不到可靠商品时不用于训练。
- 定向补充数据（2026-09-23 确认）：V2.0 第一版不预设补数据流程，不做定向补充。验收淘汰多少如实统计并报告损失；若实际损失大到明显影响训练量或难度/领域分布，再带着实际数字单独提请讨论是否补充，届时再定补充方式与上限。
- 源评测集中的无效或不可验证任务保留原记录并单独标记，不能静默删除；最终同时报告总量、可评分量和无效率。
- 验收管线（2026-09-23 确认）：
  - 第一级：代码自动检查，全量。Gold ASIN 存在、关键字段（价格 / attributes / options）完整可解析；Query 中可编程校验的硬约束（预算、instruction_options 必选规格、品牌/类别词冲突）直接对 Gold 检查。
  - 第二级：语义验收，全量，每条一次调用，对 Gold 判 satisfies / partial / no / unverifiable。Judge 固定 `jev-1.13`：凡与 Reward 同口径的判断（Gold 验收、换 Gold 确认）一律使用同一 Judge；不进 Reward 的辅助判断（画像匹配等）用 GLM。
  - 换 Gold：仅限未通过验收的训练任务。同 category/domain 检索 top-K 候选，先过第一级硬约束，再由 Jev 确认 fully_satisfies 才算成立；确认不了的退出训练。换过 Gold 的任务打标记并单独报告数量。
  - 评测口径：invalid = 商品库无解或约束自相矛盾且重配失败；unverifiable = 关键字段缺失/不可解析导致无法判定。两者均保留记录；最终报告总量 / 可评分量 / invalid 率 / unverifiable 率。
  - 评测集修复采用触发式：第一遍只验收标记、不动数据；invalid + unverifiable 合计超过约 5%（~73 条）时，冻结 holdout 前用与训练侧完全相同的流程修一轮，改动全部记录在案。
  - 人工抽检约 150 条，difficulty × domain × category 分层，重点覆盖 Judge 判 no/partial 与换 Gold 样本，用于校准 Jev 验收；若 Jev 错误率 >10% 再另行讨论换 Judge 或扩人工。
- 验收执行结果与复查定案（2026-09-24~25 完成）：
  - 全量两级验收跑完（Jev 22,467 次调用，成本 $0.70）：accepted 16,631 / semantic_fail 5,824 / hard_fail 954（规格缺失 501 + 超预算 453）/ unverifiable 12。
  - 复查环节：六个并行 subagent（轻量模型）对 5,824 条 semantic_fail 逐条盲判（分片各约 970 条，锚点对比与盲判一致率 72%，分歧双向）。发现 Jev 偏严：约六成分歧源于价格容差口径（"X 元左右"无浮动约定）、约一成源于同义表述不认。
  - 定案规则（用户 2026-09-25 确认，信复查）：复查判 fully 且 Gold 标价 >1 元 -> accepted；复查判 fully 但标价 <=1 元 -> bad_pricing（异常定价，确认坏）；复查维持 partial/does_not -> semantic_fail。
  - 最终判定：accepted 19,106（81.5%）/ semantic_fail 3,310 / hard_fail 954 / bad_pricing 39 / unverifiable 12。train accepted 18,014（82.1%），eval accepted 1,092（74.8%）。定案文件 `outputs/acceptance/final_verdicts.jsonl`。
  - Jev 判定标准修订为 v2（`jev-gold-acceptance-v2`）：instructions 写入价格容差口径（以内 <=X、左右 ±10%、区间闭合）、同义表述视为满足、主观偏好不扣分。已验收数据不重跑（放宽口径下原 accepted 必然仍 accepted，复查已完成宽口径重判角色）；v2 用于后续换 Gold 确认、Teacher 验收与灰区判分，并纳入 Reward 冻结流程。
- Jev 校准与 v3 冻结（2026-09-27）：50 条分层考卷（替代品判定 20 + 数据验收 30），DeepSeek V4.1 Flash 盲判充当裁决者。结果：整体一致率 88%（过 85% 线）、Jev 满分精确率 93%（差 2 个点）。真分歧 6 条归三类：1 条品类级放水（两轮需求判四轮为满足，教材暂保留不清）、3 条价格低位口径（Jev 卡区间下限）、2 条字段沉默口径。据此修订为 v3（`jev-gold-acceptance-v3`）：价格低于预算区间不算违规（品类与其余约束全满足时低价视为满足）；字段未提及的约束不单独判不满足（须有相反证据）。v3 为训练与评测期间的冻结版本。

### 4.3 个性化

- 不复现 ShopSimulator 论文的个性化 benchmark，也不与论文个性化分数直接比较。
- 论文画像由既有商品—指令对反向生成，可能带有目标条件偏差；V2.0 不直接把原画像—商品绑定当作独立、无偏的个性化样本。
- 现有画像数据可以作为 V2.0 自有数据的原始材料，但画像需与目标商品解耦，并检查近期搜索、收藏、购物车、订单等字段是否泄漏目标。
- 暂时只保留三个画像条件，不继续细分：
  - `no_profile`：不提供画像；
  - `aligned`：画像与购买需求相关；
  - `irrelevant`：画像与本次购买需求无关。
- 三种条件都进入训练和评测，暂定比例为 `50% / 25% / 25%`。
- 每个基础 Query 只分配一种画像条件，不复制为三个版本，也不扩大数据总量。分配时按 difficulty、domain 和 category 分层，避免三组任务难度失衡。
- 按总量折算，训练集约为 `10,981 / 5,491 / 5,490`，评测集约为 `730 / 365 / 364`；最终整数分配允许在分层抽样时做一条以内的调整。
- 画像是软偏好；当前请求中的明确约束优先。
- 现有画像原始字段先完整保留，后续通过泄漏标签和 Rubric 管理是否可用，不在数据入库阶段简单丢弃。
- 画像条件构造方式（2026-09-23 确认）：
  - `aligned`：优先复用记录自带画像，配对时按泄漏标签决定该画像可用性，不修改入库数据。训练集自带画像仅约 3,323 条（15.1%），aligned 缺口约 2,200 条由画像池语义匹配补齐：轻量 Judge 判定画像与该 Query 购买需求相关才配对，配不上的不进入 aligned。
  - `irrelevant`：画像池跨领域重配，附一道轻量语义复核，拦掉跨了领域但仍与本次需求相关的配对。
  - 同一份画像可被多条记录复用，也可在不同记录上分别充当 aligned 与 irrelevant。
  - 评测集 1,459 条中 1,343 条自带画像，aligned 基本可直接使用自带画像，无补齐压力。

- 最终 1,459 条作为冻结 holdout，不用于训练、调参、checkpoint 选择或反复修改 Rubric。
- 无效任务可以被审计和单独报告，但不能静默删除来提高指标。
- 开发集和训练过程评测从 `tag=train` 中另行划分。
- 开发集（2026-09-23 确认）：从验收后的训练池中分层抽取约 1,050 条（5%）。分层骨架为 difficulty × domain × 画像条件（3×9×3=81 格，实测最小格约 20 条，可行）；top-level category 数百个，只做覆盖度报告、不做硬分层。dev 不进 SFT、不进 GRPO，仅用于训练中评估、checkpoint 选择和 Rubric 迭代。
- 准入契约（2026-09-28 确认，与 AGENTS.md 同一定义）：
  - **评测严格成功**：完整 `gold_purchase` 终止结果且 `reward_valid=true`，正式指标唯一口径。
  - **SFT 教材准入**：`reward_valid=true` 且（完整 `gold_purchase` 或经冻结 Jev 判定 `fully_satisfies` 的替代购买）；每条替代教材保留 Jev 判定依据与完整终止结果备审计。当前教材构成：gold 5,391 / Jev 审核替代 461（partial_alternative 455 + valid_alternative 6）。
  - **数据隔离**：训练数据不得与 V2 评测集重叠。旧版 `data/evaluation/tasks.jsonl`（Final-200）退出 V2，与 SFT 语料历史重叠的 63 条仅作迁移核对，不进入任何活动评测；V2 评测集由冻结 `tag=eval` 切分构建并按稳定任务标识严格去重。

## 5. Teacher 与轨迹数据

- 已有可用 Teacher 接口：GLM Coding API；预算目前不是主要约束。
- Teacher 轨迹必须在任务 Rubric 冻结之后采集，不能先生成轨迹再倒推验收标准。
- 原始轨迹全部保留，并区分验收通过、近似成功、策略失败、主动退出和基础设施无效；不能只保留成功样本做简单拒绝采样。
- 首轮采集规模（2026-09-23 确认，2026-09-26 修订为成功即停）：约 6,000 任务，每题采样预算 3 次（T=1.0），**成功即停**——拿到一条通过验收的轨迹即停止该题采样；3 次全失败的任务进 teacher-hard 队列。每题仍只取 1 条进 SFT。任务从验收后训练池（扣除 dev）分层抽取，难度分布近似源分布但 hard 提升至 >=30%。
- 轨迹准入 = 与正式评测 Reward 同一套判分代码：硬约束通过 + Jev fully_satisfies + 轨迹良构（无基础设施错误、正常终止、token 预算内）。SFT 教的标准与 RL 奖的标准必须是同一把尺子。
- 每题只取 1 条进入 SFT（同题多次采样中 Reward 最高，同分取更短），避免单任务过采样。
- 3 次全失败的任务归入 teacher-hard 队列，留给 RL 与错误分析，不硬塞进 SFT。
- 最终评测 1,459 条永远不用于 Teacher 采集。
- RL 任务池与 SFT 任务隔离（2026-09-23 确认）：GRPO 优先使用 SFT 未使用的任务（验收后训练池扣除 dev 与 SFT 已用任务，约 12,600 道），耗尽后再循环 SFT 用过的任务。理由：背过的原题 RL 信号失真（记忆而非判断力），且组内全对无梯度。RL 任务采样延续难度分层、hard 偏重、永不触碰最终评测的规则。
- 第一阶段可以先用 GLM 多次采样建立候选轨迹和验收链路；是否以及何时加入其他 Teacher，待首轮数据分析后决定。
- 多 Teacher 的价值应通过覆盖率、错误互补性和最终训练收益验证，不能仅按模型数量堆叠。

## 5.4 提示词分层（2026-09-25 确认）

- 两套 system 提示词分离：**Teacher 采集版**（协议层 + 全部决策规则）与 **Student 基础版**（仅协议层）。
- 协议层 = 环境接口约定（工具用法、参数格式、页面合法性、守卫拒绝的应对），模型无法从数据推断，必须告知；决策层 = 购物判断力（搜索策略、选择优先级、收敛购买、循环防护），必须通过 SFT/RL 长进权重，不允许寄生在提示词里。
- **SFT 教材组装与正式评测一律使用 Student 基础版**：轨迹动作序列来自 Teacher（在其规则版提示下产生），训练样本的 prompt 换成 Student 版——动作序列被移植到裸条件下，即蒸馏。评测测的是模型自身能力，评测 prompt 同为 Student 版，保证训练-评测分布一致。
- Teacher 提示词可自由优化（提高出材率、降低采集成本），不影响 Student；错误轨迹不作为调 Student 提示词的依据。
- Teacher 版新增决策规则（源自双 Teacher 试点失败模式分析）：候选通过品类与预算门槛且满足全部明确约束时直接购买、无需继续寻找更优；删除 Reviews 相关表述（评论页在当前数据下恒为空）；结构化字段足以核验时不翻信息子页；连续多次搜索无新增合格候选时回到已核验最优候选完成购买。
- 画像拼接语两版共用："以下是该用户的画像，属于软偏好参考，与当前请求冲突时以请求为准。"

## 5.5 SFT 数据契约（2026-09-23 确认）

- 全链路关闭思考模式（Teacher 采集、SFT、RL、评测一致），控制轨迹长度；Qwen3.5 关思考运行。
- loss mask：只对模型生成的行动 token（工具调用、购买决策、文本回复）计 loss；工具 observation、系统 prompt、环境拼接内容全部 mask。
- 超长轨迹（超出训练序列长度上限）直接丢弃，不做截断保留前半段——截断轨迹等于教模型"搜索后不下单"。监控丢弃率：超过 5% 视为轨迹长度与训练长度上限配错，回头调整上限而非硬扔。
- 报错、中断等异常轨迹已在 Teacher 采集验收环节挡除，SFT 入库时仅做兜底校验（格式、mask 完整性、token 边界对齐）。

## 6. Harness、工具与可观测性

- Teacher 采集、SFT 后验证、在线 GRPO 和最终评测应尽量共用同一套环境与 Agent harness，避免多条执行路径产生协议漂移。
- Harness 负责上下文组装、工具调用、环境控制和终止；训练侧消费规范化的 request/response/trajectory 数据。
- 工具 token、observation token、模型生成 token 及其 loss mask 必须可追踪；需要验证拼接后的 token 序列与模型真实边界一致。
- 每次 rollout 至少记录任务版本、模型与采样参数、动作、observation、耗时、错误、终止原因、Reward 明细和 Rubric 版本，支持后续错误归因。
- Agent Lightning 类第三方 harness 可以作为后续适配器或对照实现，不在核心数据契约稳定前直接替换当前运行栈。
- Harness 三项设计决策（2026-09-23 确认，源自 2B 严格成功率问题的 issue 分析）：
  - **工具调用强制**：环境回合 `tool_choice=required`，每回合必须产生工具调用，取消纯文本终止（assistant_final 出口）；结束只通过 `buy_now` 或 `finish_without_purchase` 表达。移除 `think` 工具（与全链路关思考一致，且 required 下会成为无效调用出口）。混合"文本 + 工具调用"回复不拒绝，文本保留、工具照常执行；单回合单工具调用的现行规则不变。vLLM 0.25.1 / veRL 0.8.0 对 required 的支持列入兼容性冒烟。
  - **Observation 预算**：正式预算按实测 P95 定（目标 95% 页面不截断），试跑临时值 search 3072 / detail 6144 / generic 1024。截断按字段价值排序：动作信息（footer / ASIN / 价格 / 按钮）硬校验必保；正文先砍自由文本与长标题，key_attributes / available_options 最后砍。监控：按截断分桶统计成功率；与 SFT 超长轨迹丢弃率（>5% 报警）联动，预算与训练序列长度配平调整，不单边硬拉。
  - **详情子页工具**（2026-09-24 修订）：环境与工具集完全不动（符合 Environment v2.1 / tool schema v2 固定契约），`view_reviews` 保留——评论页在当前数据下内容为空，翻它最多浪费一步；同一商品同一子页（含评论页）重复访问由动作守卫拦截（不消耗步骤，回敬提示），一个轨迹只许翻一次；不做过程奖励，子页访问占比与重复拦截次数进入轨迹记录与错误归因副表。

## 7. Reward、Rubric 与评测

- 每个任务在 rollout 前生成并冻结内部 TaskSpec/Rubric；私有 gold、Rubric 和 Reward 细节不能暴露给 Agent。
- Reward 采用三段式分流：购买目标 ASIN 且任务已通过离线数据验收时，由代码直接判为 Gold；明确违反类别、预算、必选规格、动作合法性等硬条件时，由代码直接判错；只有非 Gold 且未触发硬错误的灰区候选才进入语义判断。
- 完全满足用户需求的替代商品与 Gold 商品同为满分，不再保留 Reward v3 的 `Gold=1.0、valid alternative=0.55` 目标商品特权。部分满足和明确错误的具体分值仍待后续实验冻结。
- alternative 的语义判断暂定使用 OpenRouter 上固定版本的 `typesafe/jev-1.13`，不在训练中使用会自动升级的 latest 别名。
- Jev 每个候选只做一次 Choice 判断，统一返回 `fully_satisfies / partially_satisfies / does_not_satisfy / insufficient_evidence`。这四类及其固定定义构成第一版统一语义 Rubric，不在在线 Reward 中额外拆分大量原子问题。
- Jev 的输入只包含当前实际用户请求、可选的用户画像、Agent 最终购买的真实候选商品字段、实际选择的 options 和解析后的成交价格。字段直接来自环境和商品库，不生成或补写缺失商品信息。
- Jev 输入不包含 Gold 商品、完整搜索轨迹或原始网页 DOM，避免把“满足用户需求”变成“与 Gold 相似”，也避免无关上下文干扰判断。
- 明确购物需求优先于画像；画像只在与当前购买相关时提供软偏好，不能挽救不满足明确需求的商品，也不能因无关画像而扣分。
- `fully_satisfies` 的替代商品按满分处理；`insufficient_evidence`、API 超时或调用失败标记为 Reward 不可验证，不能伪装成模型失败并直接记零。其余类别的具体奖励映射和概率阈值在中文标注集校准后冻结。
- 在线 GRPO 先本地完成 Gold/硬错误分流，再对同批灰区候选并发调用 Jev；同一任务、候选商品、所选规格和 Rubric 版本的结果允许缓存。需要记录请求哈希、模型实际版本、类别概率、耗时、重试、错误与缓存命中，持续观察 P50/P95/P99 和灰区比例。
- 实验对照设计（2026-09-23 确认）：三档主线对照，均在冻结 1,459 条上用同一套评测——原模型零样本 / SFT-only / SFT+GRPO，三档连起来展示每步贡献。不做 PPO 等其他 RL 算法对照（双卡预算限制，且项目主张是数据+验证器+飞轮流水线而非算法 superiority）。消融实验不预设，主线跑通后按实测数据决定。
- 正式评测至少区分：确定性环境结果、约束/Rubric 满足、轨迹质量、基础设施有效性。不能只汇总成一个模糊总分。
- 评测报告结构（2026-09-23 确认）：
  - 主指标 = 任务完成率：最终购买完全满足用户需求（Gold 或 Jev 判 fully_satisfies 的替代品）。分母为可评分任务数（总量减 invalid/unverifiable），无效率单独列出。
  - 小分按三维度切：difficulty（easy/medium/hard）、画像条件（no_profile/aligned/irrelevant）、domain（9 个）。画像三组小分差即个性化核心结论。
  - 次要指标副表：平均步数、搜索效率、放弃率、超时率、基础设施失败率。
  - 错误归因固定类别：买错商品（不满足/部分满足）、违反硬约束（超预算、规格错）、未购买（超时/放弃）、系统故障；bad case 按类别回流。
- Judge 需要结构化错误归因，bad case 可按错误类型回流到数据生成、Teacher 重采样、SFT 或 RL 阶段。
- Jev 校准与冻结流程（2026-09-23 确认，采用模型预标 + 用户裁决的备选方案）：
  - 校准批次共 300 条：150 条 Gold 验收场景（同时覆盖 4.2 的人工抽检，不再单独标）+ 150 条灰区替代商品场景（Reward 冻结重点）。重点抽 Jev 低置信样本，混入少量明确样本做锚点。
  - 强模型（GLM）先预标全部 300 条，与 Jev 判断对比后，只把分歧样本 + 双方低置信样本（约 100 条）交用户本人裁决；用户裁决结果即最终标准答案。
  - 通过标准：Jev 判 fully_satisfies 的精确率 >=95%（乱给满分最致命，卡最严）；整体一致率 >=85%。不达标改提示词/阈值，另抽 100 条新样本复验，防止对着答案调参。
  - 校准通过后冻结 Jev 用法（版本、提示词、阈值），训练与评测期间不再改动。
- 当前 Reward v3 已支持 `finish`、`graceful_stop` 和 `early_abstain`，但现有 `graceful_stop=-0.15` 只表示“搜索了一定范围后未发现已知合格候选”，不能证明整个商品库无解。
- 第一版中 `finish` 只用于搜索失败时及时止损，不视为正确答案。
- V2.0 Reward 数值映射（2026-09-23 确认）：以 Reward v3 数值为基础，只改两处已确认决策——
  - Gold 或 Jev fully_satisfies 替代品：1.0（v3 为 1.0 / 0.55，替代品特权取消）。
  - Jev partially_satisfies：0.25 固定档（v3 为连续 [-0.30, 0.25]，灰区判断器从代码文本匹配改为 Jev 四分类）。
  - 其余全部沿用 v3：wrong_purchase / 硬门失败 -0.85；graceful_stop / 搜索止损 -0.15；early_abstain -0.35；max_steps -0.50；repeat_loop -0.65。
  - 不可验证（insufficient_evidence / API 失败）：reward 无效并从 GRPO 组内剔除，不奖不罚。
  - 设计立场：买错罚最重（用户真金白银损失），宁可优雅退出不要乱买；GRPO 组内按相对高低归一化，v3 的间距设计直接可用。

## 8. 尚未最终确认的问题

以下内容不能视为已确定方案：

- SFT 目标轨迹数量、每题采样次数、多 Teacher 组合和验收门槛。
- 全参数 GRPO 在双卡 80GB 上的最终序列长度、batch、rollout 并发、offload 与权重同步方案，需以最小实测为准。
- 部分满足、明确错误和其他终止类型的最终 Reward 数值，Jev 概率阈值，以及 GRPO 变体或其他 RL 算法；这些晚于数据、Rubric、Harness 和评测契约。

## 9. 已阅读资料及当前结论

- ShopSimulator：保留其环境与数据作为重要基础，但不照搬目标条件画像构造或个性化 benchmark。
- veRL Agent Loop：重点关注 agent loop 的 token 拼接、工具 observation mask、response IDs 和训练/rollout 数据一致性。
- Agent Lightning：认可 harness 与 trainer 解耦、统一 tracing 的方向，但暂不增加核心实现复杂度。
- DeepSeek 数据回流相关实践：借鉴任务—环境—验证器、难度校准、失败重放和 bad-case 回流思想；不把其算法或规模直接照搬到本项目。
