# 面向长程购物 Agent 的 RL 后训练（二）：从 2B LoRA 到 9B 全参

项目地址：https://github.com/YYHDBL/shopping-grpo-longhorizon

上一篇：[面向长程购物 Agent 的 RL 后训练](/)

## 一、为什么会有 V2

V1 跑完之后 我给自己记了三笔账：

第一笔 数据太少。SFT 教材只有 428 条轨迹。模型学到的大概是"购物流程长什么样" 而不是"各种各样的需求怎么处理"。想靠几百条数据把一个模型教到能处理真实的长尾需求 我现在觉得不现实。

第二笔 模型太小。Qwen3.5-2B + LoRA 上限摆在那。当时选 2B 是算力账算出来的 没毛病 但我一直想知道 往上走一级 会发生什么。

第三笔 GRPO 的收益存疑。+1.5 个百分点的严格成功率 单次 rollout 没有方差 我自己都不信。RL 到底在这个任务上有没有用 这个问题 V1 没回答出来。

正好组里能腾出 4 张 A800-80GB。于是 V2 的目标很直接：把这三笔账全还了。模型换成 Qwen3.5-9B 全参 BF16 FSDP 数据从几百条堆到几千条 RL 那笔账 用两次完整的训练(一次失败 一次重来)去还。

先说结论免得你白读：

```text
Base（9B 零样本）    严格 39.2%   真实完成 52.8%
SFT                  严格 60.7%   真实完成 72.1%
GRPO run1（失败轮）   严格 57.4%   真实完成 70.3%
GRPO run2            写这篇的时候还在跑
```

SFT 的提升和 V1 一个量级 这个不意外。真正值得写的是后面：一次把 RL 做砸的完整复盘 和把它救回来的过程。

## 二、先把数据地基重打了

### 2.1 这次源头数据大了两个数量级

V1 是 604 个任务。V2 直接从源数据池里拿：23,421 条任务级记录。

量一大 第一个问题就不是"怎么用"而是"哪些能用"。之前 428 条我肉眼加规则就能过一遍 现在两万多条 必须有一套能规模化 又能控制质量的验收管线。

我的做法还是 V1 那个三段式的加强版：代码规则先过一遍 LLM 语义判断再过一遍 最后抽样人工抽查。但这次中间那层换了个东西 不是随便叫一个 LLM 来当裁判 而是**引入了一个专门的判定模型**。

### 2.2 Jev：一个便宜的专用判定模型

先介绍一下这个新角色。Jev 是挂在 OpenRouter 上的一个判定模型(decisions 接口) 我按 OpenRouter 的定价算了一下 跑两万次调用大概 0.7 美金。跟让它干的事情比 这个价格约等于免费 而且它是为"给定情境 判断是否满足要求"这类任务设计的 输出是结构化的判定(fully / partially / does not satisfy / insufficient evidence) 不是一段自由发挥的散文。

数据验收里最重语义的部分交给它：

- 商品和 Query 的品类是否一致
- 属性描述是不是同一回事(比如"便携"和"轻便")
- 价格约束满不满足

**但是**——这是这次踩的第一个坑——Jev 不是引入就能直接信的。

我先用它全量跑了 22,467 次判定 把数据分成了接受/拒绝。然后随机抽了一批"被拒"的 找了六个互相独立的盲判(不让它们看到 Jev 的结论)去复核。结果发现 Jev 偏严：

- "40 元左右"买了个 42 元的 Jev 判不满足。但站在真实用户角度 42 就是"左右" 合理
- "礼盒装"和"含礼盒"这种同义表述 Jev 偶尔判不匹配

复核把 2,475 条从"拒绝"里救了回来 也顺手剔掉了 39 条定价异常的。

> **🌟**
> 这轮我学到的事情是：**LLM 裁判引入之后 先校准 再全量 再冻结**。
> 直接信任何一个裁判(包括人)都会把标尺本身变成噪声源。

最后定案：

```text
源数据        23,421
accepted      19,106 （81.5%）
semantic_fail  3,310
hard_fail        954
bad_pricing       39
unverifiable      12
```

### 2.3 画像：这次真的做了

ShopSimulator 论文里本来就有个性化用户画像 V1 我没做。V2 把它做进来了 而且做得比"加个画像"多一步——我想要的不只是"有画像" 而是能**验证画像到底有没有用 有没有害**。

画像池 4,666 份。有个脏点要先处理：773 份画像里泄漏了任务的关键词(画像里直接写了用户要买的东西)。这种画像等于把答案塞给模型 必须在渲染层剔除掉行为字段之外再人工标记。

然后是三种条件的分配：

```text
aligned    （画像与需求一致）      52%
irrelevant （画像与需求无关）      24%
no_profile （无画像）             24%
```

353 条三轮重配都配不上的 降级成无画像。这个三条件设计后面在评测里直接给我交了一份"画像效应"的答卷 这是 V2 我最喜欢的实验设计之一 后面第八节说。

### 2.4 一个意外发现：teacher-hard

数据重打的过程中翻出来一批很有意思的题：**两个不同的 Teacher 模型 各给三次机会 都没能做出来的任务 一共 727 道**。

这批题我单独存了一个桶。它们的价值在 RL 阶段才显出来——SFT 教材里没有它们的成功轨迹 也就是说模型从没被教过怎么做这种题。留着给 RL 去自己探索。

## 三、双 Teacher 采集：分治 + 成功即停

V1 采集用单个 Teacher 一个模型跑全部。V2 数据量大了 20 倍 我改成两个 Teacher 分治：GLM-5.3-Flash 和 DeepSeek V4.1 Flash 各分一半任务 各 8 并发。

两个模型脾气不一样。GLM 一次通过率 90.4% 基本不用管。DeepSeek 一开始只有 44% ——不是它笨 是它太"谨慎" 总在核验细节上绕圈。给它加了一版收敛性提示词(明确告诉它确认关键约束后就要下手)之后提到了 87.5%。

> **🌟**
> 每个 Task 最多给 3 次机会 成功一条就停。不搞"刷到全对为止"——
> 刷出来的数据是 Teacher 的上限 不是教材 应该反映真实可得的成功分布。

最终：

```text
6,579 个任务 → 5,852 条教材轨迹
hard 任务占 34.6%
平均 5.9 步
teacher-hard 桶 727 题
token 消耗：输入 4.78 亿 + 缓存命中 5.33 亿 + 输出 871 万
```

### 3.1 提示词分层：Student 版和 Teacher 版

这是 V2 我自己挺得意的一个设计。

Teacher 采集时要给它完整的决策规则(什么时候该买 什么时候该停 怎么核验)——不然它做不出来题。但 SFT 训练用的 prompt 如果也带这些规则 学到的就是"读题+执行说明书" 而评测的时候用户不会附说明书。

所以 prompt 分两层：

```text
Teacher 版 = 协议层（工具怎么用）+ 决策规则层（怎么判断该买了）
Student 版 = 协议层
```

采集用 Teacher 版 教材的动作序列配上 Student 版的 prompt 进 SFT。**动作是 Teacher 的 提示词是 Student 的** ——prompt 移植过来 蒸馏就发生了。评测也用 Student 版 大家公平。

## 四、Harness 的三针缝补

V1 那套 Harness 的哲学(观察投影、Action Guard 当最后一道安全网)全部保留 V2 只缝了三针 这三针都是看轨迹看出来的：

第一针 `tool_choice=required`。删掉 think 工具 删掉纯文本出口。V1 的时候模型偶尔会"说话"而不是"动手" 一说话这一步就废了。直接从协议上把出口焊死。

第二针 子页单次访问拦截。同一个商品详情子页(Description/Features/Reviews/Attributes)看第二次 基本就是模型在原地打转。看过一遍的信息直接拦掉 把页面按钮重新递给它。

第三针 观察预算分级改成 3072/6144/1024(搜索页/详情页/普通页)。比 V1 的 1536/4096/768 放了一档 因为 9B 模型核验能力上来了 多给一点正文换来更少的误判。并行工具调用统一丢弃多余的 只留第一个——训练时一个动作一个环境状态 不然 Advantage 对不齐。

另外一个 SFT 侧的重要契约：**被 Guard 拒绝的动作段落不进 Loss**。5,852 条轨迹里有 941 个被拒段(分布在 684 条轨迹上) 这些段落的 token 训练掩码记 0——模型不该学"怎么发出会被拒绝的动作" 但也没必要因为它发过就惩罚上下文里其他正确的部分。

改完之后测试从 V1 的几十个涨到 143 个 然后到 167 个。Harness 是缰绳 缰绳本身得先结实。

## 五、Reward v4：档位表、灰区升级、和我自己挖的两个坑

V1 的 reward v3(博客里叫 v3 仓库里也 v3 为了不混淆 这篇开始 V2 的版本叫 **v4**)用了之后 暴露了三个问题：

1. `valid_alternative_purchase` 一刀给 0.55 太粗。替代品有"几乎完美"和"勉强凑合" 0.55 把它们压成一个数
2. 分数档位之间的缝隙里藏着漏洞(下面讲 0 分漏洞)
3. repeat_loop -0.65 这种和环境守卫耦合的档位 环境一改语义就漂移

### 5.1 v4 的表

先过两道硬门 类目和预算。不过 直接 -0.85(wrong_purchase);证据不足无法核验 记 0.0 并标记无效——这个 0 不是"中性" 是"这题不算数"。

```text
gold_purchase（买到目标商品）          1.00
partial（买到部分满足的替代品）         0.25
graceful_stop（充分检索后礼貌收尾）     -0.15
early_abstain（没怎么查就放弃）        -0.35
截断（预算耗尽没走到终局）             -0.50
wrong_purchase（硬门不过）             -0.85
基础设施无效                           0.00（不产生学习信号）
```

### 5.2 灰区升级：Jev 进 Reward

替代品那档 0.25 对"其实买得很好只是 ASIN 不同"的轨迹太亏了。v4 的做法：硬门通过的替代购买 进入**灰区判定**——由 Jeval 判定是否完全满足用户需求 判 fully_satisfies 直接升到 1.0 和 gold 同权。

判定结果按 `(instruction, asin, options, price)` 做缓存——同一个任务 8 条采样里有 3 条买了同一件替代品 只判一次 Jev。整个 RL 跑下来灰区调用几百次 成本几美分 可以忽略。

为什么敢在 reward 里放一个 LLM 判定？因为标尺是冻结的(校准流程见 2.2 判定标准写死版本) 判定是结构化输出的 而且失败时降级回 0.25 不阻塞训练。**Reward 里可以有 LLM 但它必须是"可缓存 可降级 标尺冻结"的** 这是我的底线设计。

### 5.3 我自己挖的坑之一：截断 0 分漏洞

v4 最初版本里 撞到 token 上限或步数上限被截断的轨迹 记 0.0。

某天对着 reward 分布看的时候发现不对：截断 0.0 比礼貌收尾 -0.15 还高。也就是说 **模型拖着不结束 把预算耗光 是比"好好收尾"更优的策略**。这是我自己给自己埋的激励漏洞。

修复：截断单独成档 -0.5 排在早退(-0.35)之下 买错(-0.85)之上。梯度方向变成：买到 > 礼貌收尾 > 早退 > 拖满预算 > 买错。每一档都在推模型"要么买 要么果断收尾"。

### 5.4 我自己挖的坑之二：连续长度惩罚 加了又撤

第二个坑更微妙。看数据发现 SFT 模型平均跑 20 轮 同样的题 Teacher 平均 6 轮就买完了——模型在过度探索 浪费 3 倍多的轮次。我于是设计了一个软阈值的连续轮次惩罚：12 步以内不罚 12 到 35 步线性拉满 罚上限 0.10。

数值上精心算过：0.10 恰好是最小档差(0.20)的一半 结果档的排序不可能被翻转 只在同结果内部起"同样买对 少逛的赢"的作用。看起来很完美。

用户(就是我老板 我也是我老板)把它毙了。理由很简单也很有力：**这个任务的池子里 hard 和 teacher-hard 占了 45% 长轨迹可能包含必要的搜索、比较和规格确认 仅凭步数 无法判断哪些操作是浪费**。惩罚步数等于惩罚认真做难题的模型。

于是撤掉 轮次只留在观测指标里。绕了一圈 回到 V1 博客里写过的一句话——"多两步可能是无意义地重复搜索 也可能是认真核验"。区别是这次我拿着数据绕的 结果一样 但我知道为什么了。

> **🌟**
> Reward 设计里最容易犯的错不是数值没调好
> 而是往一个结果导向的目标里掺过程导向的直觉。
> 掺之前先问：这个"过程偏好"有没有反例？hard 任务就是反例。

## 六、训练环境大换血：Docker、NCCL 和三天排障

V1 租一张 RTX 6000 装完就跑。V2 换到自己组的 4×A800 服务器 第一天就被上了一课。

死锁链是这样的：Qwen3.5 需要新版 vLLM(0.25 系) → 新 vLLM 绑定 torch 2.11 → torch 2.11 只有 cu130 构建 → **服务器驱动 535 跑不了 cu130**。而能兼容驱动的旧 vLLM 不认识 Qwen3.5 的模型结构。宿主机上无解。

组里其他人怎么跑的？看了一眼 都在 Docker 里——镜像里带了 CUDA 兼容层 用容器的用户态驱动绕开宿主机内核驱动的版本限制。照做。容器里的最终栈：

```text
verl 0.9.1 + vllm 0.25.0 + torch 2.11(cu130) + transformers 5.10.4
```

然后是 NCCL。

训练一启动 Ray 的 4 个 worker 报 **"Duplicate GPU detected: rank 1 和 rank 0 在同一张卡上"**。这个坑我卡了快三天。试了各种 NCCL 环境变量、IPC 配置、GPU 绑定 都没用。最后我和 agent 一起对着报错栈一层层往下挖 挖到的真相是：训练框架的一个初始化钩子里 import 了 veRL 触发 CUDA 初始化 这一步发生在 Ray 给每个 worker 分配显卡**之前** CUDA 把"全机 8 张卡"的映射缓存住了 等 Ray 再来设置"你只能看见这 4 张"的时候 已经晚了。

解法是一个环境变量 `PYTORCH_NVML_BASED_CUDA_CHECK=1` 让设备可用性检查走 NVML 而不真正初始化 CUDA 运行时。一行 解决。但这三天让我记住了一条纪律 并在后面又撞了一次(第十节)：

> **🌟**
> 训练容器里 每一个"顺手 import"都是在动 GPU 初始化时序。
> 非必要 不导入。

## 七、SFT：这次教材够吃了

### 7.1 训练

5,852 条教材 挖掉守卫拒绝段和参数污染的 最终 **5,542 条训练 + 110 条验证**。172 步 走完 val loss 从 0.292 单调降到 0.278 没有过拟合迹象。9B 全参 4 卡 大约三个小时。

### 7.2 评测换了个基准

V1 的 Final-200 退役了。V2 的正式评测集是**冻结的 1,092 题**——从 accepted 数据的 eval split 里按难度×领域×画像条件分层抽出来 和 SFT/GRPO 的所有数据严格按 task 隔离。指标是两个：

- **严格完成率**：环境终局判 gold_purchase 才算(和 V1 口径可比)
- **真实完成率**：严格完成 + 灰区里被 Jev 判 fully_satisfies 的替代购买(用户视角"任务完成了吗")

### 7.3 三臂的前两臂

```text
Base（9B 零样本）  严格 39.2%   真实 52.8%
SFT                严格 60.7%   真实 72.1%
```

几个细节值得说：

**Base 不是 0%了。** V1 那次 Base 严格成功率 0% 是因为当时的 prompt/harness 没给 2B 模型留活路。V2 的 9B 零样本能到 39.2% 说明大部分"交互协议"层面的能力 大模型是自带的 SFT 教的主要是**这个环境的协议细节和决策习惯**。

**画像效应出来了。** 按画像条件分桶：

```text
aligned（画像与需求一致）    <  no_profile  <  irrelevant（画像无关）
```

注意 aligned 反而最低！合理 fooled 的解释：画像给了模型额外的"用户偏好"信号 当画像和当前需求不完全一致时(哪怕构建时是一致的 渲染出来的文本总有错位) 模型会被带偏。而且这个排序在 Base 和 SFT 两臂上方向一致 所以不是教材的锅 是画像这个信号本身的副作用。

**错误形态在变。** SFT 之后剩的错误里 partial 替代购买 237 条 repeat_loop 68 条 顶格 35 条——比"完全不会做"难一个层级的问题 SFT 已经把下限抬完了 剩下的是判断力问题。这正是 RL 该出场的位置。

## 八、GRPO 第一次：熵是怎么炸的

### 8.1 配置：V1 的判断 直接继承

run1 的配置基本是 V1 判断的延长线：

```text
n=8（每题采 8 条）  batch 8 题 = 64 轨迹/步
lr 1e-6 恒定（12 步 warmup）
无 KL（连 reference model 都不加载）
优势不做 std 归一化（Dr.GRPO 风格）
ppo clip 0.2   temperature 1.0
1000 题（难度分层 + teacher-hard 桶）× 125 步
```

无 KL 的理由 V1 博客写过：SFT 起点稳 用 LoRA + 小 lr + clip 兜底 足够保守。V2 虽然从 LoRA 换成了全参 但 lr 还是那么小 我觉得一样保守。

**这个判断错了。而且错得很有教学意义。**

### 8.2 先岔开讲：OOM 三连

训练前 3 步就 OOM 了三次 才跑到正题。三版的排查记录(这段工程味重 但对跑长序列 RL 的人应该有用)：

**v1 版** 崩在训练前向算 log-prob 的地方。对着报错栈和 agent 一起查 定位到崩溃点是 `log_softmax` 作用在一个已经物化出来的 logits 张量上——GRPO 要逐 token 算新旧策略比值 必须**完整物化 [序列长度 × 15 万词表] 的 logits** 22k token 的轨迹就是 6.7G 一个张量 加上 log_softmax 中间量和反向 一张 80G 的卡被顶穿。

我先试了常规路线：参数和优化器状态全部 offload 到内存。峰值从 79G 降到 57G 过了第一步 但余量太小 第二步换个重批次还是贴着天花板。

然后我去翻了翻训练框架的源码 找到了正解：`use_fused_kernels`。它内置了一个分块输出头 **512 个 token 一块 直接拿 hidden states 乘输出头权重 从头到尾不物化完整 logits** 反向逐块重算。开了之后：

```text
峰值 57G → 43.8G    训练反而快了 20%
```

顺带搞明白了一件事：为什么 V1 用的 liger-kernel 救不了这里。liger 最省显存的融合交叉熵(FLCE)是"吃 hidden states 直接吐一个标量 loss" 而 RL 需要**每个 token 的 log_prob** 拿不到中间量就算不了策略比值——所以框架源码里干脆写死禁用了 FLCE。SFT 能用的东西 RL 未必能用 这是结构性的不是配置问题。

我当时跟人说"压这个峰值只有三条路：减序列、offload、砍生成上限"。第四条就躺在源码里 等我去翻。

> **🌟**
> 说"不存在"之前 先说"我没找到"。这两句话的差别
> 在三天以后会变得非常明显。

### 8.3 回到正题：熵爆炸

OOM 修完 训练顺利开跑。前 41 步一切正常 熵在 0.36~0.48 的小带子里晃 我还挺得意。

step 45 开始爬。step 55 加速。step 75 到 1.85。step 87 到 **6.0**。

```text
0.44~0.65（step 40-55 正常波动）
0.6 → 1.4（step 55-70 爬升）
1.4 → 3.4（step 70-85 加速）
4.2 → 6.0（step 86-90 爆炸 接近均匀随机）
```

熵 6 意味着采样分布接近瞎猜——**step 85 之后模型产出的训练数据基本是噪声 它在用自己的噪声训练自己**。step 93 手动停了。

有意思的是验证集(贪婪解码)的表现：

```text
step 0    0.671
step 25   0.490（掉坑）
step 50   0.698（回升）
step 75   0.697
```

贪婪的 argmax 对分布变平是有抵抗力的 所以验证分没崩 但采样已经废了。这个"表面还活着 内部已经在发散"的形态 如果不盯熵根本看不出来——这也是为什么 run2 我把一堆组级指标塞进了日志。

### 8.4 为什么炸：组内信号一直是好的

第一反应是"没信号导致的漂移"？查了数据 不是。GRPO 的优势是组内中心化的 我把每步的优势极值拉出来 **±1.0~1.5 从头到尾存在**——每批 64 条里永远有"买对的和买错的"对比 学习信号从来没断过。

信号是好的 还炸 说明问题在"刹车"上。机制我复盘成一句话：

**熵涨 → 采样更随机 → 失败率涨 → 组内分差反而更大(±1.5) → 推力更强 → 熵更涨。** 一个自增强的死循环 而我把所有刹车都拆了——无 KL(没有参照物) 优势不归一化(奖励差距直接变成推力) lr 恒定(尾段不收油)。

V1 说"LoRA + 小 lr + clip 够保守"——LoRA 本身就是一根缰绳(可训参数不到 2% 策策跑不远)。全参 9B 没有这根缰绳 我却以为"lr 小"能替代它。**被自己的实验证伪 是 V2 最值钱的一课。**

### 8.5 打捞：step50 的评测

炸了不等于白跑。checkpoint 每 25 步一个 挑了 step 50(熵 0.48 还在健康区 验证 0.698 和 step 75 打平)走完整评测：

```text
GRPO run1 step50   严格 57.4%   真实 70.3%
SFT                严格 60.7%   真实 72.1%
```

**小亏。** 严格口径 -3.3 个百分点。错误形态的变化很有指向性：gold 少了 36 条 repeat_loop 多了 33 条——策略变"抖"了 开始重复动作 直到被守卫掐掉。发散的种子在 warmup 结束后不久(step 25 验证掉坑就是证据)就埋下了 所谓"挑未发散的 checkpoint"救不回已经发生的学习污染。

RL 这一轮 不仅没赚 还小赔。记入账本。

## 九、GRPO 第二次：三件刹车 + 把测量补齐

### 9.1 刹车组合

run2 的配置是run1 的病理报告直接开出来的：

```text
KL 锚：use_kl_loss=true, coef 0.01（reference 全程冻结 常驻内存）
lr：2e-7（run1 的 1/5）8 步 warmup 后 cosine 衰减到 0.1 倍
batch：16 题 × n=8 = 128 轨迹/步（独立任务翻倍 单步梯度噪声减半）
top_p 1.0 + rollout IS 修正（修 rollout 引擎和训练引擎的概率差）
```

三个参数各管一件事：**KL 锚管"每步走不远" batch 管"每步方向准" lr 管"步子小"**。run1 证明了只把步子变小是不够的 方向抖的时候小步也会累积漂移。

KL 锚上线后有件好玩的事：前两步 kl_loss 精确等于 0 不是 bug——warmup 期 lr 只有 2.5e-8 权重的相对变化量级是百万分之一 **比 bf16 的舍入分辨率还小** 权重在前向精度下一个 bit 都没动 和 reference 逐位相同 KL 自然是 0。step 3 开始有 8.95B 个参数里恰好卡在舍入边界上的那批翻转了 KL 跳到 4e-4。数值的诚实有时候超出直觉。

### 9.2 动态采样：这次先测量 再干预

GRPO 每题采 8 条 如果 8 条全同分(gold 全 gold 错全错) 这组优势全零 白烧算力。V1 我自己写过过滤逻辑 run2 有个更基本的问题要先回答：**这种零方差组到底占多少？**

run1 的数据落盘之后算了一下：**47.9%**。将近一半的 rollout 算力花在零学习信号的组上。这个数字出来之后 "要不要开动态采样"就不是一个判断题了 是算术题。

run2 开了框架自带的 DAPO 式过滤：零方差组淘汰 换新题补齐(换新题而不是死磕原题 不会死循环)。实测效果：

```text
run1（无过滤）    零方差组 47.9%
run2（开过滤）    进入训练的组 零方差率 0.0%   连续 5 步
```

代价是每步生成量增加 步时从 22 分钟涨到 30 分钟左右。用 30% 的墙钟换 100% 的信号有效 我觉得划算。

### 9.3 把仪表盘补齐

run1 的教训之一是"看得见的不够多"。run2 加了三样：

**组级指标**。框架只记全批次的 reward 均值 组内标准差和零方差比例算了但不记。我在 agent 的协助下给训练循环打了个小补丁 `group/reward_std_mean` 和 `group/zero_variance_ratio` 直接进训练日志和云端看板。中间还踩了个坑：想当然地按想象的 uid 格式写了分组逻辑 结果落盘数据一对 全是单成员组——uid 的真实结构和我猜的不一样。**改分组逻辑之前 先看真实数据。**

**轨迹级落盘**。每步的每条轨迹 reward 原样写盘 组级指标全部可离线复算。

**SAVE_AND_STOP**。任意时刻 touch 一个标志文件 训练在下一个安全点保存 checkpoint 然后退出。原理是个很朴素的事实：一步内权重只在最后 optimizer 更新的那几秒变化 rollout 阶段(占步时三分之二)权重保持上一个完整步的状态——所以中途打断直接存 就是"回退到上一个完整步" 最多损失半步的生成算力。60 多个小时的训练 必须有这个开关。

### 9.4 一个回旋镖：hook 导入纪律

run2 冒烟的时候 NCCL Duplicate GPU **又回来了**。上次修好的东西复发 是最让人头皮发麻的故障类型。

排查路线和上次一样 我和 agent 对着日志一层层剥 最后收敛到嫌疑面：训练钩子里新加的补丁 import 了训练器主模块 而这个 import 实测会触发 CUDA 初始化(不 intuicio 的部分：连环境变量都拦不住的那种)。第六节的教训重演 只是这次是自己的代码。

修复不是打补丁式的"再调一下"而是立规矩：**钩子里只留最小导入集 其余所有补丁(包括这次的)改成延迟生效**——挂一个导入监听 等业务代码正常导入目标模块之后 再把补丁打上去 那时候 Ray 的环境已经就绪 时序天然安全。改完冒烟通过。

## 十一、思考

### 11.1 V1 说对的说错的

这次回头看 V1 的判断 有意思的地方在于**对错的比例和我想的不一样**：

说对的：不加长度惩罚(绕一圈数据后回归)、动态过滤有价值(这次量出来 47.9%)、评测不加权成总分(三臂对照全靠拆开的多面板才能看清错误形态)。

说错的：**"保守配置可以替代 KL"**——这是被 run1 直接证伪的核心判断。LoRA 是缰绳 全参没有 缰绳必须换成 KL。

半对半错的：评测先行。V2 的顺序还是 reward→评测→数据→训练 但多了一条：**测量先于干预**。零方差率 47.9% 测出来之前 "要不要动态采样"是靠直觉吵 测出来之后是算术题。V1 的"评测先行"评的是模型 V2 补上的是评"训练过程本身"。

### 11.2 agent 时代的工程方式

这个项目一半以上的排障(NCCL、OOM 三连、熵爆炸、钩子复发)是我和 agent 一起完成的 我的角色从"写代码的人"变成了"提问题、定方向、拍板的人" agent 负责把源码翻个底朝天把证据摆出来。几次关键突破都是这个模式的产物：我给方向和怀疑 它逐条对着安装的源码核实 把"我觉得"变成"源码第几行就是"。

但 V2 我也学到了这个模式的纪律。agent 说"只有三条路"的时候 其实是"它找到三条路"——**最终拍板的人要为"没找到的那条路"负责** 所以关键结论必须要求它给出证据链而不是结论本身。

### 11.3 教训清单(给自己)

- 说"不存在"之前说"我没找到"
- 改分组/解析逻辑前 先看真实数据落盘长什么样
- 训练钩子里非必要不 import 任何东西
- 往 reward 里掺过程偏向前 先找反例
- 长训练必须有"随时可停可存"的开关
- 引入任何 LLM 裁判 先校准 再全量 再冻结
